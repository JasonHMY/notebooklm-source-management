## B-google-research — What Google changed (web research)

Google renamed NotebookLM to Gemini Notebook on 2026-07-16. The app moved to notebook.google.com, and the old notebooklm.google.com address redirects there: HTTP 302 in late July, then 301 from about 2026-08-24, according to third-party tests. The extension already handled this in 26.8.2 (2026-08-02). Its storage is keyed by notebook ID, not by host, so saved data survived the move. I found no public report of a sources-panel redesign between August and October 2026. The September web refresh changed the home grid and the Studio icons, and the October Studio changes did not touch the Sources panel. The biggest product change is native source labels: auto-labeling plus manual add, rename, delete and move, with several labels per source, which reached 100% of users on 2026-05-05. These overlap the extension's one-level folder value, but Google still has no nested folders, manual ordering, custom tags, multi-select bulk delete, search across existing sources, or undo. Several new findings matter. The extension's name and short_name are built on the Google trademark, which conflicts with the Chrome Web Store branding rules. Sources can now change outside the open tab, through the Gemini app Connected App (2026-10-23), Workspace Studio automation and Drive auto-sync. The extension's native-DOM text heuristics only cover English and Chinese for label view and source counts. Chrome MV3 platform changes in 2026 are minor for this extension.

### B1 [medium] Extension name and short_name use the Google trademark 'GeminiNotebook' as the product name, against Chrome Web Store branding rules

- Category: google-compat · effort S · confidence medium · verdict: adjusted (auditor severity high) · needs live check: False
- Locations: _locales/en/messages.json:2-6; _locales/es/messages.json:2-6; _locales/zh_CN/messages.json:2-6; manifest.json:3-4; README.md:1; https://developer.chrome.com/docs/webstore/branding

**Evidence.** All three locales set extName = "GeminiNotebook-Source-Management" and extShortName = "GeminiNotebook". The short_name is only the Google mark. A grep of README.md, PRIVACY.md, _locales and docs found no trademark attribution and no 'not affiliated with Google' text. The Chrome Web Store branding page (developer.chrome.com/docs/webstore/branding, last updated 2018-06-11) says: "Don't use any Google trademarks or any confusingly similar marks as the name of your extension". It allows 'for' / 'for use with' / 'compatible with' plus the product name with the TM symbol, and it requires attribution in the description. The impersonation policy (last updated 2022-11-01) bans implying that a product is "authorized by, endorsed by, or produced by another company". Competitors follow this pattern, for example 'NotebookLM Tools for Gemini Notebook™' (CWS, v2.2.4, 2026-10-26) and 'Gemini Notebook Organizer (NotebookLM)', whose listing says it is "not affiliated with or endorsed by Google". Live listing (fetched 2026-10-27): 'GeminiNotebook-Source-Management' v26.10.4, updated 2026-10-04, 389 users.

**Impact.** The next store submission could be rejected, or the listing could lose visibility or be taken down for trademark or impersonation reasons. That would affect all installed users. Enforcement looks inconsistent (similar listings are still live), so the risk is real but its timing is uncertain.

**Recommendation.** Rename to a descriptive name that uses compatibility wording, such as 'Source Folders for Gemini Notebook™', and give it a non-trademark short_name. Update all three locales, the README title, the actionTitle strings and the store listing in the same release. Add a 'Gemini Notebook is a trademark of Google LLC; not affiliated with Google' line to the listing, README and PRIVACY. Do this before a reviewer forces it, while there are still few users.

**Verifier.** The evidence holds. _locales/en/messages.json:2-6 sets extName "GeminiNotebook-Source-Management" and extShortName "GeminiNotebook", and manifest.json:3-4 uses them. A grep of README, PRIVACY, _locales and docs found no trademark or non-affiliation text. I re-fetched developer.chrome.com/docs/webstore/branding (last updated 2018-06-11), which says "Don't use any Google trademarks or any confusingly similar marks as the name of your extension" and requires "for" / "compatible with" wording with the TM symbol. I lowered the severity from high because git history shows the previous name was "NotebookLM Source Management", which was also mark-led and passed review across many releases. The live listing (fetched 2026-10-27) shows the current "GeminiNotebook-Source-Management" 26.10.4 has already been accepted. The risk is real but has not shown up through enforcement. The live listing overview also still calls the product "NotebookLM Source Management", so the listing copy itself is out of date.

### B4 [medium] Native-DOM text heuristics for label view, select-all and source counts only cover English and Chinese, while Gemini Notebook's UI is localized

- Category: google-compat · effort M · confidence medium · verdict: adjusted (auditor severity medium) · needs live check: True
- Locations: src/content/content-native-label-detector.js:42-50; src/content/content-native-label-scan.js:14-17; src/content/content-panel-dom.js:42; src/content/index.js:285-289; src/content/content-source-actions.js:206-207

**Evidence.** content-native-label-detector.js: SOURCE_VIEW_SWITCH_TEXT_PATTERN, NATIVE_LABEL_ENTRY_POINT_TEXT_PATTERN, SELECT_ALL_TEXT_PATTERN (/\bselect\s+all\b|全选/i) and NATIVE_SOURCE_SORT_CONTROL_PATTERN contain only English and Chinese alternatives. content-native-label-scan.js parseNativeLabelSourceCount accepts only /(\d+)\s*(?:sources?|items?)/ or 来源/项目. By contrast, content-source-actions.js:206-207 NATIVE_DELETE_TEXT_PATTERN and NATIVE_RENAME_TEXT_PATTERN include French, German, Spanish, Japanese and Korean (eliminar, renombrar, löschen, 削除, 삭제 and others). The extension ships an es locale, so Spanish-speaking users are an explicit audience. Gemini Notebook is sold worldwide, and the Workspace post (2026-07-16) applies to all customers.

**Impact.** Where icon or aria fallbacks do not match, users with a non-English, non-Chinese Gemini Notebook UI may hit failed native label import (source counts not parsed, so imports show as 'source_count_mismatch' or 'unavailable'), wrong list/label view detection, or native sort and select-all controls being treated as label titles.

**Recommendation.** Treat the select-all row structurally: a checkbox in the panel header before the first source row, or the checkbox whose checked state mirrors all rows, instead of by text. Add Spanish strings at least (seleccionar todo, fuentes, vista de lista) to the detector and count parser, matching the extension's own es locale. Add a Spanish-UI fixture test asserting that list view stays LIST. Fix the impact description: unparsed counts disable the import completeness check.

**Verifier.** The regexes are as described. content-native-label-detector.js:42-50 (SOURCE_VIEW_SWITCH_TEXT_PATTERN, NATIVE_LABEL_ENTRY_POINT_TEXT_PATTERN, SELECT_ALL_TEXT_PATTERN, NATIVE_SOURCE_SORT_CONTROL_PATTERN) and content-native-label-scan.js:14-17 cover only English and Chinese. content-source-actions.js:206-209 is multilingual. Coverage is not uniform, though: index.js:289 NATIVE_LABEL_RETURN_TO_LIST_PATTERN already includes Spanish ('volver.*lista|vista\s+de\s+lista'), and icon patterns (label_auto, view_list) are language-agnostic. The stated impact is partly wrong. parseNativeLabelSourceCount returning null is consumed at content-source-sync.js:1157-1172, and content-native-label-import.js:43-51 only reports 'source_count_mismatch' when expectedSourceCount is non-null. An unparsed count therefore skips the completeness check and makes import more permissive. Imports are not marked as mismatched. It means a partial label scan can be accepted silently, which is a different risk. The bigger real risk I found is content-source-sync.js:1112-1118. Any button or role=button inside the panel that contains a checkbox and whose text does not match SELECT_ALL_TEXT_PATTERN ('select all|全选') counts as an active label-view control. That feeds getSourceViewInfo (:1707-1731), which can classify the view as LABEL. A localized 'Seleccionar todo' row could cause this, if it is a button container. That depends on live DOM structure.

### B-M2 [medium] In a non-English or non-Chinese native UI, a checkbox-bearing select-all button can be counted as an active label-view control and flip view detection to LABEL

- Category: google-compat · effort S · confidence medium · verdict: verifier-found (auditor severity medium) · needs live check: True
- Locations: src/content/content-source-sync.js:1093-1121; src/content/content-source-sync.js:1707-1731; src/content/content-native-label-detector.js:46

**Evidence.** isActiveNativeLabelViewControl returns true for any panel button or role=button element that has a descendant input[type=checkbox], non-empty text of 120 characters or less, and text that does not match SELECT_ALL_TEXT_PATTERN (/\bselect\s+all\b|全选/i) or NATIVE_SOURCE_CONTROL_TEXT_PATTERN. getSourceViewInfo then sets inferNativeLabelTitles when activeLabelControls.length > 0. It returns SOURCE_VIEW_KIND_LABEL if label entries are found, and otherwise returns LABEL at 0.78 confidence before falling through to LIST at :1733. A Spanish 'Seleccionar todo' or German 'Alle auswählen' row passes the text exclusion. Whether the native select-all row is a button container is not verified.

**Impact.** If the live DOM matches this shape, users with a non-English, non-Chinese Gemini Notebook UI in plain list view could have the view misdetected as label view. That would affect view-switch sync, label-title inference and possibly row scanning, and could break the core manager in those locales.

**Recommendation.** Identify the select-all control structurally: a checkbox outside every source row, before the first row, whose state mirrors the rows. Do not rely on localized text. Extend SELECT_ALL_TEXT_PATTERN with at least Spanish as a stopgap, and add a fixture test with a localized select-all row in list view that asserts LIST is detected.

## A-native-dom — Coupling to Google's native Gemini Notebook DOM, URLs and text

The extension depends heavily on Gemini Notebook's private DOM: about 60 selectors, plus aria-label/text regexes (mostly English and Chinese), Material icon ligature text, Angular CDK overlay structure and a few structural walks. Its destructive paths are defended in depth. Delete only proceeds after: an identity-validated row, fresh menu-item scoring that aborts when ambiguous, a confirm dialog that must name the target title, and an inventory preflight. Data-pruning paths are also guarded: a zero-row scan preserves state, and an unresolved remap is skipped. So a DOM change is unlikely to delete the wrong source or empty folders outright. The main weaknesses: (1) there is no DOM health check or kill switch, so if row parsing breaks while the panel is still found, the manager still mounts and hides the native list behind an empty or stale manager; (2) several core features depend on assumptions the smoke fixture never exercises and that may not hold on the real page, including explicit totalHint attributes (single and batch delete fail safe without them), stable `data-*` tokens, and non-nested row wrappers; (3) the stable-token heuristics accept generic or positional attributes, and a stable token outranks every other identity signal, which could silently remap folder membership; (4) much locale-sensitive matching is English/Chinese only. The smoke fixture is a hand-written idealized DOM, which is why real-page drift would go undetected by CI.

- Dependency inventory (for the owner). URL: `/notebook/<id>` path segment (index.js 2250-2257); hosts notebook.google.com and notebooklm.google.com (manifest). Panel: `[data-testid="source-panel"]`, `.source-panel`; header `.panel-header` or else firstElementChild; content `[data-testid="scroll-area"]`, `.scroll-area-desktop`, `.sources-list-container`, `.scroll-area`. Rows: `[data-testid="source-item"]`, `.single-source-container` plus broad label-row selectors (`[role=listitem]`, `mat-list-item`, `[data-source-id]`…). Title: `[data-testid="source-title"]`, `.source-title`. Checkbox: `input[type=checkbox]`, `[role=checkbox]`, `mat-checkbox`/`.mat-mdc-checkbox`. More button: `[aria-label="More options"]`, `.source-item-more-button`, ligatures `more_vert|more_horiz|overflow_menu`. Type icon: `mat-icon[class*="-icon-color"]` ligature text, with an iconMap of `video_youtube`, `drive_pdf`, `picture_as_pdf`, etc. Processing/failure: progressbar/mat-spinner/aria-busy/data-state plus en/zh/es text and ligatures `error|warning|cancel`. - Native flows the extension drives on the user's behalf: checkbox click (enable/disable a source for chat context), More menu → Rename (opens native inline rename), More menu → Delete → native confirm button click, row click or More → details, list/label view toggle and label-menu 'return to list', expansion of collapsed label groups, and Escape/body.click to dismiss overlays. Delete is the only irreversible one. It has seven independent guards (validated row identity, fresh-menu diffing, ambiguity abort, dialog must name the target and no other title, unique identity in a complete inventory, coordinator project/instance binding, post-delete N→N−1 survivors proof). A wrong-source delete therefore needs several simultaneous failures. The realistic risks are the inverse: delete never works (A2), or a non-delete native action (e.g. a 'Remove from label' item scoring as delete in label view) gets executed and then reported as a failure.
- Data-safety layering is strong. A zero-row scan always preserves state; a first load with unresolved stored keys stages a placeholder merge; a remap with unresolved weak identities is skipped; a complete scan with missing keys needs two identical observations. The weak point is upstream: identity is entirely DOM-derived (A3, A9), so garbage identity in means confidently-wrong identity out.
- Architectural recommendation: introduce a single versioned 'NativeDomAdapter' contract module. It would own every selector, text pattern and ligature list (currently spread across content-config, source-descriptor-helpers, content-source-sync, content-source-actions, content-native-label-detector, index.js and styles.css), expose `probe()` returning a structured health report, and gate mounting and the hide-CSS on that report (A1). This makes Google redesigns a one-file change with a measurable pass/fail. The existing code already has the pieces (getSourcePanelState, getSourceScanCompleteness); they just are not used as a kill switch.
- The decision to keep the native list in the render tree (visibility:hidden plus position:fixed) and drive Google's own menus is reasonable for MV3 without private APIs. Keep it, but route the native destructive flows behind the probe. If the probe fails, disable native rename/delete in the menu with an explanatory tooltip rather than attempting them.
- Locale handling should prefer structural and ligature signals over UI text. Where text is unavoidable, cover all locales Google ships (or at least those of the extension's own users) via `\p{L}`-aware patterns and per-locale tables, tested with a localized fixture.

## C-state-storage — State, persistence, migrations and background storage protocol

The persistence core is carefully engineered: background writes are serialized per notebook in a FIFO, revision-guarded, and atomic (one chrome.storage.local.set call writes the primary, the rotated backup and the history together). Future or invalid schemas fail closed, and critical saves keep a sessionStorage recovery copy. The main weaknesses are long-term storage economics and how folder membership stays tied to source identities. Every changed save appends a full snapshot to history. Nothing ever removes the keys of deleted or abandoned notebooks. The manifest has no unlimitedStorage permission. So heavy users will eventually hit the 10 MB quota, and once they do, every notebook stops accepting saves that grow its state. Source keys are hashes of title|aria-label|icon unless a heuristic DOM attribute provides a token. After a redesign that changes how titles or icons render, the mutation-sync path permanently drops the folder membership of unresolved sources after two identical "complete" scans and saves the result. Recovery then depends on a backup that keeps one generation and an edit-count-bounded history that rotates within minutes. Docs are mostly accurate, with a few concrete drifts (group `name` vs `title`, an undocumented sessionStorage key, history-migration wording). There is also one dead module (content-state-repair.js) and two wasted full-storage reads on every page load.

## E-architecture — Overall architecture and maintainability

The core design (hide Google's native source list, render a full Shadow-DOM replacement, push selection and actions back into Google's DOM) still works in the synthetic fixtures. It is fragile against Google's ongoing redesigns for three reasons. Hiding the native list fails closed: there is no health gate. Knowledge of Google's DOM is spread across about 10 files plus styles.css. Persisted source identity comes from DOM heuristics that the tests only exercise through a path the real page may never provide. Maintainability is limited by src/content/index.js: 7557 lines, 221 top-level functions, 77 mutable closure variables and 55 runtime properties shared with other modules. On top of that, a dual dependency-resolution style (368 typeof-default fallbacks plus globalThis service-locator lookups in 19 helpers) hides wiring errors. The overall approach should not be replaced, but it should change shape. First, consolidate all native-DOM knowledge into one adapter with a probe/health check that unhides the native list when the probe fails. Second, move stateful feature orchestration (view switching, rename watcher, batch delete, source repair, label import, command registry) out of index.js. Third, generate the hand-maintained module registries from the manifest. A bundler is optional and not the bottleneck. One module (content-state-repair.js) has been dead in production since 2026-09-08, and several docs claims about load order and assembly are inaccurate.

## H-ui-i18n-a11y — UI styling, design-system drift, accessibility and i18n

The Shadow-DOM manager UI is mostly self-contained and well tokenised. It uses an Apple-HIG look on purpose, so a Gemini Notebook visual refresh will mostly not break it. The weak points are at the edges where it touches the page. First, the global overlay stylesheet injects an unscoped 'Google Symbols' @font-face and a `.google-symbols` rule into Gemini's own document for the manager's whole lifetime, but the drag-ghost path that justified it is now dead. Second, the panel background is sampled from Gemini while every foreground token follows the OS prefers-color-scheme, so contrast is only guaranteed while the Gemini theme and the OS theme agree. Most locale strings already say Gemini Notebook. The remaining i18n issues are terminology and plural quality, the missing `lang` attribute on the shadow root, and native-DOM text heuristics that only understand English and Chinese.

## Critic

### Overall recommendation

Keep the overall approach and change how it fails. Do not rewrite it. There is no public consumer API. Augmenting Google's Angular-owned list in place would be more fragile, and a side panel would still have to proxy native checkboxes while losing in-context drag. So the overlay design (Shadow-DOM manager, background-owned revision-guarded storage, driving Google's own controls) stays. Three reasons favor reshaping it rather than continuing as-is. (1) The highest-impact risks are not individual bugs but one chain: a partial Google DOM change flows from the scan into a hidden native list, a persisted tree with lost placements, and native checkbox clicks that change which sources Gemini answers from (A1/E1, C2, X1, X3). One DOM-contract/scan-health gate in front of those three side effects removes most of that risk for small effort. (2) Nobody knows whether the extension matches the live page today. Stable IDs, delete total-count attributes, the default native view and URL shapes are all unverified, and every test runs against a self-authored fixture. A live read-only check plus a dated, sanitized real-DOM fixture has to come before choosing fixes. (3) Google's native labels now cover basic grouping and may be the default view (X2, B3). The product has to work alongside labels and lead with what is not native (nested folders, ordering, tags, safe bulk delete, search, undo, backup), with a non-trademark name (B1). What to keep: the overlay UI, the background FIFO and revision guard, the frozen storage keys and export format, the layered delete safety, and the el()-only DOM construction. What to change, in order: step 0, secure the repo (push, move out of iCloud). Then live verification and a real-DOM fixture. Then the scan-health gate that also covers native-selection enforcement. Then concrete bugs: disable toggle across SPA/tabs (F1), UI-only fields flooding history (C-M1), Classic Move-out sweep (D3), unbounded storage with unlimitedStorage and a cross-notebook cleanup (C1), and a migration path when a stable ID appears (C2). Then consolidate native selectors, text and host knowledge into one adapter with structural/icon-first, locale-agnostic signals, and incrementally extract stateful features from index.js, starting with view switching. What to drop: the HTML5 drag adapters and dead CSS (D1), content-state-repair.js (E5), the restyling of native Material menus (H5), the unscoped global `.google-symbols` rule (rename the bundled font to a private family instead), and, as a product decision, Classic mode's placement invariant. Main risk: the gate's thresholds. Too strict, and the extension pauses itself on legitimate states (empty notebooks, slow hydration, virtualized long lists), which users would see as breakage. Too loose, and nothing changes. Mitigate by basing it on positive evidence (native rows visible but unparsed), logging verdicts in diagnostics before enforcing, and tuning against the live captures. A second risk is refactor churn in index.js against about 60k lines of tests that reach private accessors. Keep the gate and the bug fixes small and land them first, and defer the large extraction.

### Themes

- Fail-closed coupling to an unverified DOM: the extension hides Google's list, persists remaps and clicks native checkboxes from the same scan, with no single health verdict (A1/E1, C2/A-M1, X1, X3). One DOM-contract probe that gates all three side effects addresses the highest-risk chain.
- Tests prove internal logic, not compatibility: 1,897 unit tests and the smoke suite run against a hand-written fixture that always matches the primary selectors, has clean data-source-id, an English UI and no native menus or dialogs. Nothing has been checked against the live page (A10, G3, E7), and the smoke harness itself is unreliable (G1, G2). The open questions that decide severity (stable IDs, total-count attributes, default view, URL shapes) are all live checks.
- Identity is the weakest point: folder membership, tags and native selection all hang on DOM-derived keys (title|aria|icon hash or heuristic tokens). Generic tokens, fingerprint churn, a new stable ID with no migration path, and positional collisions all lead to silent remaps (A3, A9, C2, E7, B2).
- Google's product moved toward the extension: native labels (default organization), out-of-band source changes (Gemini app, Workspace Studio, Drive sync), and localized UIs. The extension still assumes list view, in-tab edits, and English/Chinese text (X2, B2-B4, A6, H10).
- Storage economics and recovery: full-snapshot history on every save (including UI-only resizes), one-generation backup, no cross-notebook cleanup, and no unlimitedStorage. Recovery depth is therefore minutes of edits, and the quota is reachable by heavy users (C1, C3, C4, C-M1).
- Accumulated weight and drift: a 7.5k-line index.js, about 700 lines of dead HTML5 drag code, a dead state-repair module, duplicated selector and host lists, docs that misstate load order, privacy scope and storage trust, and a trademark-led name. These raise the cost of every Google-driven fix (E3, D1, C9/E5, E2, F6, B1).

### Gaps found by the critic

#### X1 [high] Every list-view scan pushes the extension's stored enabled state into Gemini's native checkboxes, so identity or remap errors silently change which sources Gemini answers from

- Locations: src/content/content-source-sync.js:2840-2872; src/content/content-source-sync.js:2932-2945; src/content/content-source-sync.js:2340-2348; src/content/content-tree-interactions.js:2773-2858; src/content/content-view-state.js:240-265; src/content/index.js:6045

**Evidence.** In the scan merge, a known key keeps the extension's stored value (`enabled = oldSourcesMap.has(source.key) ? Boolean(oldSourcesMap.get(source.key).enabled) : nativeCheckboxState`). On first load the stored value also wins (`enabled = hasResolvedEnabled ? Boolean(resolvedSourceState.enabled) : nativeCheckboxState`). Then, unless options.syncNativeSelection === false (set by only one caller, index.js:6045), every scan outside label view runs `sourcesByKey.forEach(source => syncSourceToPage(source, isSourceEffectivelyEnabled(source), { preferStoredCheckbox: true }))`. syncSourceToPage enqueues a real native checkbox click whenever shouldToggleNativeCheckbox(checkbox, desiredState) is true. isSourceEffectivelyEnabled is `source.enabled && areAllAncestorsEnabled(source.key)`, so the folder tree drives the native selection. The partial-loading merge (2340-2348) does the same. No area audit examined this path, which links the identity, remap and native-selection issues.

**Impact.** This turns several findings that were rated as internal state problems into user-visible changes to the AI's context. (a) A3/C2/A-M1: when a later scan drops the folder membership of sources that sat in a DISABLED folder, those sources are no longer behind a disabled ancestor. Their effective state flips to enabled, and the same scan clicks them on in Gemini's native list. The user's chat then uses sources they had excluded, with no message. A positional or colliding stable token (A3) can also apply one source's enabled state to another row. (b) If Gemini keeps source selection server-side or across surfaces (Gemini app Connected App, mobile, another tab), any selection changed there is reverted to the extension's stored copy the next time the notebook opens in list view. This needs live verification.

**Recommendation.** Treat native selection as Gemini-owned during passive scans. Push selection to Gemini only on user-initiated transitions (folder toggle, isolate, move into a disabled folder, explicit restore or import). On scans, adopt the native checkbox state for known keys, or record a divergence and surface it, instead of enforcing the stored state. At minimum, skip enforcement on any scan that is partial, has unresolved or ambiguous identities, or changed placements in the same pass. Log a `native_selection_enforced` count. Add a test where a source in a disabled folder loses membership and no native click is issued.

#### X2 [medium] Gemini's native label view (default organization since May 2026) puts the manager into an empty compatibility shell, so folders are hidden by default for many users

- Locations: src/content/content-render.js:1784-1800; src/content/content-tree-interactions.js:2783-2797; src/content/index.js:3325-3338; src/content/index.js:4738-4760; src/content/index.js:6508-6517; tests/smoke/extension-smoke.spec.js:887-935

**Evidence.** render(): `const isNativeLabelView = sourceViewInfo.kind === 'label'; ... if (isNativeLabelView) { ... patchChildren(listContainer, fragment) /* empty */ ... }`, so no folders or sources are rendered. syncSourceToPage refuses label view (`reason: 'not_list_view'`). On attach, a native view change copies the native kind into sourceViewDisplayKind (index.js:6508-6513), and getSourceDisplayViewInfo then keeps the native list visible. restorePersistedSourceViewDisplayKind switches only when a saved display kind exists. The Google Help Center (cited in B3) says that with 5+ sources 'your sources will be automatically organized', i.e. label view is the native default. The smoke test that currently fails ('keeps NotebookLM label view visible in compact compatibility mode') tests exactly this path, although it fails earlier at extension-ID registration.

**Impact.** A new user, or any notebook with no saved view preference, opens a 5+ source notebook in Gemini's label view and sees only a compact extension header with no folders. The core value is invisible until the user finds the view switch. It also means the per-folder enable toggles cannot sync selection in this view. Area audits treated label view as a detection problem (A5, B4, H10), not as the default user experience.

**Recommendation.** Live-verify the default native view for a fresh 5+ source notebook. If label view is the default, make the first run explicit: a one-time prompt in the compact shell ('Show my folders' → switch to list view), and remember the choice per notebook, ideally as a global preference. Optionally render the folder tree read-only in label view, with a note that selection sync needs list view. Do not auto-click label or relabel controls without consent (see A5).

#### X3 [high] No circuit breaker spans the scan → remap → save → native-click chain; the guards are local to each step

- Locations: src/content/content-source-sync.js:2802-2830; src/content/content-source-sync.js:2932-2945; src/content/content-source-sync.js:3005-3022; src/content/content-source-partial-sync-guard.js:95-127; src/content/index.js:6223-6235

**Evidence.** In one mutation-driven sync pass, the scan result does three things: it decides placement (remapExistingStateToCurrentSources, guarded only by the two-observation partial-sync rule), it is persisted (`saveState()` when the signature changes, 3017-3022), and it drives native checkbox clicks (2935-2945). Meanwhile the native list stays hidden (setNativeSourceListHidden). Each step has its own local guard (zero-row preserve, unsafe-remap skip, first-load staging), but nothing evaluates whether the scan as a whole looks healthy before letting all three side effects run. A1/E1 (hide), C2/A-M1 (drop and save) and X1 (native clicks) are three symptoms of the same missing gate. Area audits reported each one separately.

**Impact.** A partial Google DOM change can, within about a second and with no user action, hide the native list, persist a tree with lost placements (pushing good snapshots out of the edit-count-bounded history, C3) and change Gemini's source selection. Recovery depends on the user noticing, opening history before about 20 more saves, and re-selecting sources by hand.

**Recommendation.** Introduce one `scanHealth` verdict computed once per scan. Inputs: the native candidate-row count versus parsed manageable rows, the share of stored keys that resolve only through fallbacks or not at all, a concrete view kind, and whether stable tokens are unique. Gate all three side effects on that verdict: hide only if healthy, drop placed records or save remaps only if healthy, push native selection only if healthy. When the verdict is unhealthy, keep the native list visible, keep placeholders, skip native clicks, write a reason-tagged history checkpoint, show a banner and log a `dom_contract_violation`. This is the A1/E1 probe with a wider scope. It is one small module plus three call-site checks, not a rewrite.
